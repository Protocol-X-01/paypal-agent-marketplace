# Channel3 shared request budget

Production Channel3 requests use a durable, deployment-wide counter before the provider request is made. Search, catalog browse, similar-product lookup, and exact-product refresh each reserve one request. A paginated continuation reserves again. Timeouts and provider errors still use the reservation because the request may have reached Channel3.

The store reserves three global fixed UTC windows in one PostgreSQL transaction. The app-owned demonstration proposal is 2 requests per fixed second, 30 per fixed minute, and 100 per UTC day. These are deliberately conservative application caps, not Channel3 quotas. The migration leaves all three values `NULL`; a trusted operator must explicitly configure them before production calls can run.

Each window resets on its UTC epoch-aligned boundary; none is rolling. A full fixed-second allowance can be consumed on each side of a boundary, so 2 per fixed second permits at most 4 requests in any rolling one-second interval. That is below Channel3's documented default lookup limit of 5 per second, provided the same API key is not used by other clients during that interval. The 30-per-minute and 100-per-day windows can still allow nearly twice their configured amounts in rolling minute and 24-hour intervals when usage straddles a boundary. Before production quotas are configured, verify that the provider's current reset semantics are compatible. If they differ, use a verified conservative cap that accounts for these boundary bursts or change this implementation to match the confirmed provider windows. Do not enable production calls until that match or conservative cap is established.

The transaction locks the day row, then the minute row, then the second row in that deterministic order. It reads `clock_timestamp()` only after all three locks, validates the configured quotas and stored counters, then increments all three or none. A denial updates no counter. Missing or null quota, missing migration/row, invalid state, timeout, or database error fails closed with HTTP 503. Exhaustion returns HTTP 429 and `Retry-After`, set to the latest reset among exhausted windows. The per-IP in-memory limiter remains as a local fairness backstop, but it is not the shared budget.

This counter covers the app's Channel3 API requests only. Product image/CDN downloads and requests made after opening a retailer page are outside the counter and any quota configured here.

## Provider allowance and app-owned demonstration caps

Channel3's [rate-limit documentation](https://channel3.ai/docs/faq/rate-limits) currently lists, for new/default API keys, 10 requests per second for search, 5 per second for lookup, 10 per second for other endpoints, and a shared daily allowance of 10,000 requests. The proposed app caps (2 per fixed second, 30 per fixed minute, 100 per UTC day) apply across all Channel3 request types made by this deployment, but they do not count any use of the same key outside this app and do not reserve space against other key users. Provider limits and account plans can change.

At 100 requests per UTC day, this deployment can reserve at most 3,100 API requests in a 31-day month. That is a request ceiling, not a credit or bill guarantee. Channel3's [pricing page](https://channel3.ai/docs/pricing) currently lists 1,000 free monthly credits and $0.007 per credit after that; search, browse, and similar-product requests cost one credit each, while product retrieval is listed as free. Actual charges depend on the account's current plan, credit balance, endpoint mix, and other use of the shared key. Review the current account billing and provider terms before production configuration; do not infer a cost solely from the local request count.

The migration intentionally creates all three quota rows with `request_limit = NULL`. The application has no guessed default or environment-variable override. A trusted operator must review current limits and billing, then explicitly set all three app-owned values in one administrator transaction. Reduce a live limit only after reviewing current counters; if usage is already above the new limit, requests remain denied until the affected window resets.

## Database and runtime setup

This can use the existing dedicated Render PostgreSQL instance; it does not require a new paid database. The schema contains only three aggregate counters and three administrator-set quota rows, with no customer identifiers, addresses, search terms, or product data.

1. A database administrator applies [the forward-only migration](channel3-request-budget-migration.sql) through the separately reviewed migration workflow. It creates separate non-login owner/runtime roles, a Channel3 schema, three fixed counter rows, three initially unconfigured quota rows, and a narrowly scoped `SECURITY DEFINER` reservation function. The migration is not automatic and is not part of application startup.
2. After checking provider limits, account plan, billing and reset behavior, the administrator may choose to configure the proposed demonstration caps (2/second, 30/minute, 100/day) or another reviewed conservative set. Set all three positive integer limits in one transaction; leave any value `NULL` until it is reviewed, and production stays fail-closed.
3. Choose a separately reviewed database connection and configure `CHANNEL3_BUDGET_DATABASE_URL` in Render. A dedicated `paypal_channel3_budget_runtime` login can provide a budget-only credential after its creation and permissions are verified. Alternatively, only if the broader access is consciously accepted, a reviewed grant can let the existing `paypal_auth_runtime` role call the function and the budget setting can contain the same URL as `AUTH_SESSION_DATABASE_URL`. A second setting does not create a separate credential or narrow its permissions; coordinate both settings whenever the auth credential or endpoint changes. Either URL must use verified TLS and contain no query parameters or fragments. Never place a credential in `.env.example`, a Postman collection, logs, or a checked-in environment file.
4. With the dedicated role, verify that its effective privileges are limited to database `CONNECT`, schema usage and `EXECUTE` on `reserve_request()`, with no `TEMP`, `CREATE`, direct quota/counter-table access or customer-auth access. With the existing auth role, the function grant is additional to its existing read/write access to customer-auth tables and its auth-budget access; do not describe that credential as budget-only. In either case, public database/schema/function privileges must be reviewed, and neither runtime role may assume the budget owner. The function owner is a separate `NOLOGIN`, non-superuser role with a fixed `search_path`; its table references are schema-qualified, and `PUBLIC` execution is revoked. PostgreSQL retains `ADMIN OPTION` on the owner role for the migration administrator that creates it; that trusted administrator can change the budget objects. The operator credential remains separate from runtime credentials.
5. Deploy the API change only after the approved database configuration is ready, then verify status handling and quota enforcement against the exact deployed commit. A missing setting or migration intentionally makes the Channel3 routes return 503 rather than calling the provider.

`render.yaml` declares the database URL with `sync: false`; an existing Render service requires a separately reviewed manual setting change. This repository change does not apply the SQL, create a role/credential, set quota values, connect Render, or deploy.

## Test and extension boundary

The isolated PostgreSQL test exercises multiple independent pools, all three atomic windows, denial without partial consumption, UTC window expiry, deterministic lock order, dedicated-role CONNECT without TEMP/CREATE, that role's inability to alter quota/counter rows or access the auth schema, missing/unconfigured data, invalid window state, lock/database failures, and pool recovery. Synthetic route tests verify `Retry-After` propagation for second-, minute-, and day-window exhaustion. These tests do not show that the existing auth role lacks auth access, and they do not call Channel3 or establish the live account allowance, provider reset semantics, account billing, or hosted configuration.

This implementation is Channel3-specific. A later OpenAI explanation budget can reuse the transaction pattern, but it needs an independent provider quota, configuration, counter scope, and least-privilege decision. Do not charge OpenAI requests against the Channel3 allowance.
